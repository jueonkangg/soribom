# 수업 실사용 진단 기록

2026-10-12, main `0701344`를 반영한 guhyeon에서 구현했다. 새 작업은 커밋·푸시 전이다.
음성·자막·말하기 입력·이름·메일 주소·비밀번호·예외 메시지는 이 진단 파일에 저장하지 않는다.
정상 수업 기록 TXT와는 별도다. 기존 터미널 출력에는 말하기 원문 일부가 있을 수 있어
터미널 전체를 파일로 저장하는 방식으로 대체하지 않는다.

## 시험 순서

1. 기존 앱을 종료하고 바탕화면 소리봄을 재실행한다. 터미널에 `[진단] 기록 위치:`가 나온다.
   앱은 한 개만 실행한다. 다음 명령으로 실제 기록 생성 여부를 확인할 수 있다.

   ```bash
   cd /data2/code/soribom
   .venv/bin/python scripts/analyze_diagnostics.py
   ```

2. 약 50분 동안 자막을 사용한다. 몇 차례 과목을 바꾸고 말하기도 여러 번 사용한다.
3. 중간에 마이크를 분리·재연결해 자동 복구를 확인한다. 필요하면 다시 연결 버튼을 사용한다.
4. 누락·화면 멈춤·잡음·느려짐을 발견하면 대략적인 시각과 증상을 적어 둔다.
   실제 오인식은 로그에 원문이 없어 사용자 설명·스크린샷과 대조해야 한다.
5. ESC 등으로 앱을 정상 종료하고 위 요약 명령을 실행한다. 이후 Codex에게 로그 검토를 요청한다.
   로그는 프로젝트 폴더에 있어 다시 업로드할 필요 없다. 재실행하면 새 세션이 되므로
   시험 후 여러 번 재실행했다면 어떤 시간대의 시험인지 알려준다. 요약 명령은 마지막 세션을 선택한다.

## 위치·한도·장애

- `diagnostics/runtime.jsonl`과 `runtime.jsonl.1`~`.4`. `.4`가 가장 오래된 파일이다.
- JSON 한 줄에 이벤트 하나를 저장하며 시간대가 포함된 시각·세션 ID·경과 시간을 기록한다.
- 기본 10초 간격으로 자원을 측정한다. 파일당 2MiB, 현재 파일 포함 약 10MiB 한도다.
  한도를 넘으면 오래된 내용을 순환 삭제한다. 앞부분이 없으면 요약에서 알려준다.
- 파일 권한 600, Git 제외. 설정은 `src/config.yaml`의 `diagnostics`다.
- 파일 쓰기는 워커 하나가 처리한다. 큐는 256건이고 가득 차면 진단 이벤트만 버리고
  버린 개수를 기록한다. 자막·마이크 콜백에서 디스크 쓰기를 기다리지 않는다.
- 디스크·권한 오류면 진단 기록을 중단하고 터미널에 안내하며 앱은 계속 동작한다.
  정상 종료 시 남은 이벤트를 비우고 종료 기록을 쓴다. 종료 대기는 최대 2초이며
  디스크 응답이 매우 느리면 마지막 이벤트는 남지 않을 수 있다.
- 강제 종료·전원 차단에서는 종료 기록이나 마지막 일부가 없을 수 있다. 종료 기록 부재만으로
  OOM이라고 단정하지 않는다. 실행 중인지, 시스템 로그·시험 시각과 함께 판단한다.

## 기록 항목과 해석

| 항목 | 의미·제약 |
|---|---|
| 앱/녹음 RSS, 시스템 MemAvailable | 현재 메모리 추세. RSS는 최대치가 아닌 현재 상주량이다. 프로세스 간 공유 메모리를 단순 합산하지 않는다. GPU 전체 사용량을 직접 측정한 값은 아니다. |
| queue_depth/capacity, queue_overflows | 자막 대기 큐 길이와 포화 횟수. 증가하면 STT 처리 속도·입력 속도를 함께 본다. |
| queue_dropped_blocks, resets | 큐 초기화 때 버린 블록 수·횟수. 재연결·포화·정상 종료 정리도 포함하므로 모든 수치를 처리 지연에 의한 누락으로 해석하지 않는다. |
| stale_input_blocks, audio_gaps | 오래돼 제외한 수음 블록 수와 콜백 시각 간 큰 간격. 녹음 파이프 내부에서 버린 블록의 정확한 총량은 알 수 없다. |
| stale_results | 연결 세대가 달라 게시를 거부한 횟수. 자막뿐 아니라 늦게 도착한 방향 표본도 포함한다. |
| mic_start, mic_failure, retry, device_status | 녹음 시작 시도·장애·수동 재시도·연결 상태 전환. 첫 녹음 시작도 mic_starts에 포함한다. 장애 사유는 capture_error/process_exit/input_timeout/driver_error로 구분한다. |
| caption의 stt_duration_s | 실제 transcribe 호출 시간. 모델 초기 로딩은 별도 준비 단계다. |
| speech_age_s, dispatch_delay_s | VAD가 판정한 마지막 음성 끝부터 전사 시작·UI 신호 전달까지. 무음 대기·큐 지연을 포함한다. 실제 화면 렌더 완료 시각은 아니다. |
| has_text, 필터별 세그먼트 수 | 빈 전사·무음/낮은 신뢰도/힌트 나열 제외 여부. 빈 결과가 곧 실제 발화 누락을 뜻하지 않는다. |
| direction_known | 해당 자막에서 방향이 확정됐는지. 방향 정확도나 사람 신원 검증은 아니다. |
| tts_start/synthesis/playback/end | 요청·합성·sd.play 반환·재생 완료/실패. 재생 제출까지의 시간은 스피커의 실제 소리 시작 시각과 다르다. |
| error의 stage/error_type | 실패 구간과 예외 종류. 개인정보 노출 방지를 위해 메시지는 저장하지 않는다. |
| note_save | 실제 저장 콜백의 성공·실패. 저장할 변경이 없는 주기는 이벤트가 없다. |
| session_end.clean | GUI와 정리 경로의 정상 종료 여부. 모든 기능의 성공이나 기록 저장 성공을 보장하는 값은 아니다. |

짧은 메모리 급증은 10초 주기 사이에서 놓칠 수 있다. 일정한 RSS 상승은 누수 후보이며
GPU 캐시·모델 준비와 구분해야 한다. 텍스트 없는 수치 로그로 STT 정확도나 잡음 자체를 판정하지 않는다.

## 검증

기록 큐 과부하·순환 파일 한도·JSON 유효성·권한·원문 필드 제외·디스크 실패 시 앱 지속·
정상 종료 배출·자막 통합 경로의 기록 생성·TTS 실패 후 재시도 기록을 자동 검증했다.
전체 87개 테스트 통과(9.954초). 모의 로그를 생성해 요약 CLI에서 메모리·자막 지연·
USBError·정상 종료가 올바르게 출력되는 것도 확인했다. 모의 USBError는 실제 장치 장애 보고가 아니다.
모의 시험은 실제 50분 GPU·USB·BT 사용 시험을 대신하지 않는다.
