# 기록 자동 저장·말하기 안정성 확인

2026-10-11 기록·말하기 구현 단계에서 자동 테스트 44개 통과. 사용자가 기록·말하기 보호 기능을 테스트했다고 보고했다.
요일/과목은 새로 구현했고, 실제 장시간 통합 시험의 조건·결과는 미기록이다. 커밋·병합 상태는 Git에서 확인한다.

## 달라진 동작

- 기록은 기본 30초마다 변경이 있을 때 저장하고 정상 종료 시 마지막 내용도 저장한다.
- `notes/`에 실행 시각·UUID가 포함된 TXT 하나를 만들고 같은 파일을 갱신한다.
- 쓰기가 끝난 임시 파일로 교체한다. 저장 실패 시 이전 파일과 메모리 기록을 보존한다.
- 상단 저장 안내는 실패 이후에도 유지하고 다음 저장 성공 시 정상 안내로 바뀐다.
- 말하기는 한 번에 하나만 처리하고 성공한 문장만 지운다. 실패하면 입력을 남겨 재시도한다.
- 한 번에 기본 200자까지 말할 수 있다. 제한과 저장 간격은 `src/config.yaml`에서 설정한다.
- 기록 보기·저장 파일·메일 본문에 날짜의 한국어 요일과 과목을 표시한다. 과목을 바꾸면
  이후 발화부터 새 과목으로 기록하며 여러 과목은 구간별로 구분한다.

강제 종료 시 마지막 저장 이후의 구간은 잃을 수 있다. 저장 파일은 파일 관리자로 열어 읽는다.
앱에서 이전 수업을 자동 복원하거나 기록 전체를 지우는 기능은 추가하지 않았다.

## 팀원이 확인할 순서

1. ReSpeaker·블루투스 스피커를 연결하고 바탕화면 소리봄을 실행한다. 모델 준비와 연결 완료를 기다린다.
2. “자동 저장 확인 첫 번째 문장”이라고 말해 자막을 만든다. 약 30초 후 상단에 저장 시각이 나타나는지 확인한다.
3. 프로젝트의 `notes/`에서 가장 최근 TXT를 열어 문장을 확인한다. 두 번째 문장을 말하고
   다음 저장 후 같은 파일에 추가됐는지 확인한다. 앱을 종료한 뒤 마지막 문장도 있는지 확인한다.
4. 곧바로 앱을 다시 실행해 다른 문장을 기록하고 종료한다. 이전 TXT가 유지되고 새 수업 TXT가 생성됐는지 확인한다.
   날짜의 요일·과목이 맞는지 확인하고, 과목을 바꿔 새 발화를 추가했을 때 이전 발화의 과목이 유지되는지도 확인한다.
5. 입력칸에 “질문이 있습니다”를 넣고 말하기를 누른다. 준비·재생 중 버튼과 입력이 비활성화되고,
   자막은 계속 갱신되는지 확인한다. 재생 완료 후 입력이 지워지고 다시 입력할 수 있어야 한다.
6. Enter와 버튼을 빠르게 여러 번 눌러도 한 번만 말하는지 확인한다. 200자보다 긴 문장은
   소리 대신 분할 안내를 보여주고 입력을 남겨야 한다.
7. 시스템 출력 장치와 스피커 연결을 확인한다. 출력 오류가 실제 발생하면 실패 안내와 원문 보존을
   확인하고, 연결을 복구한 뒤 같은 문장을 다시 말한다. OS가 다른 출력으로 자동 전환하면 앱은
   이를 실패로 판단하지 못하므로 BT를 끄는 것만으로 오류 테스트가 된다고 단정하지 않는다.
8. 밝은/어두운 테마 모두에서 상태와 오류 안내를 읽을 수 있는지 확인한다.

저장 실패·앱 강제 종료는 자동 테스트에서 임시 폴더와 모의 기록으로 확인했다. 오류가 생기면
화면 안내, 발생 시점, 마지막 저장 TXT 유무, 실제 출력 장치를 알려주면 원인 추적에 도움이 된다.

## 자동 검증 범위

```bash
QT_QPA_PLATFORM=offscreen .venv/bin/python -m unittest discover -s tests -v
```

기존 26개에 기록 9개·말하기 UI 4개·Speaker 4개·앱 종료 저장 1개를 추가했다. 저장 중 추가된 자막의 다음 저장,
파일명 분리, 권한 600, 저장 오류 시 이전 파일·임시 파일 정리, 별도 프로세스 강제 종료 후 저장본
유지, 연속 요청 차단, 출력 오류 후 재시도, 빈 파형·출력 중단 등을 검증한다.
SMTP는 모의 객체로 처리하며 실제 메일을 보내지 않는다. GPU 모델·USB·BT 실장치는 이 검증에 포함되지 않는다.

## 모든 재생에서 지지직거릴 때

이번에는 실제 GPU와 CPU로 합성해도, 순수 톤과 유튜브를 틀어도 같은 잡음이 났다.
GPU 파형 두 문장의 최대 절댓값은 0.241/0.391로 음량 초과·NaN/무한대가 없었다.
스피커는 SBC/A2DP 모드였고, 해당 스피커만 연결을 끊고 재연결하자 사용자가 깨끗해졌다고 확인했다.
재연결 후 기존 Speaker.say 경로에서도 정상 완료됐다. 기존 연결 세션과 관련된 출력 문제로
좁혔지만, 무선 간섭·버퍼·드라이버 중 정확한 내부 원인은 확정하지 않았다.

1. OS 블루투스 설정에서 현재 스피커의 연결을 끊는다. 페어링 삭제·초기화는 하지 않는다.
2. 같은 스피커를 다시 연결하고 시스템 출력 장치로 선택한다.
3. 유튜브 또는 짧은 테스트 음성과 소리봄 말하기를 비교한다.

이번 환경의 Wi-Fi는 2.4GHz였다. Bluetooth와 같은 대역을 사용하므로 간섭 후보지만, 이번 잡음의
확정 원인으로 단정하지 않는다. 대역과 간섭 설명: [Intel Bluetooth FAQ](https://www.intel.com/content/www/us/en/support/articles/000005821/wireless/legacy-intel-wireless-products.html).

## 2026-10-13 Bose 잡음 재발 조사

- 사용자는 소리봄 말하기뿐 아니라 Jetson에서 재생한 다른 소리에서도 잡음이 난다고 확인했다.
  따라서 TTS 합성 모델만의 문제로 볼 수 없다. 정확한 원인은 아직 미확정이다.
- Bose 연결과 기본 출력, SBC/A2DP 프로필을 확인했다. USB Bluetooth 장치의 전원 관리가
  `on`이어서 USB 자동 절전이 활성화된 상태는 아니었다. Wi-Fi는 2.4GHz를 사용하고 있었다.
- 44.1kHz의 440Hz 시험 톤을 재생하며 Bluetooth 출력 전의 소프트웨어 모니터 신호를 기록했다.
  유효 신호 구간에 10ms 이상의 무음 단절이 없었고 파형에 비정상 값이 없었다.
  이는 Bluetooth 전송 이후의 실제 소리 품질까지 보장하는 결과는 아니다.
- 출력 버퍼를 2048 프레임으로 늘린 시험에서도 사용자가 잡음을 확인해 강제 버퍼 설정을 해제했다.
- PipeWire 처리 주파수를 44.1kHz로 강제하는 시험에서도 사용자가
  '약간 지지직거린다. 마지막엔 괜찮아진 것 같기도'라고 답했다.
  해결로 판정하지 않고 `clock.force-rate=0`, `clock.force-quantum=0`으로 원복했다.
  영구적인 오디오 설정 변경은 하지 않았다.
- Wi-Fi 절전 해제는 실행 권한 및 실행 중 설정 적용 제한으로 적용하지 못했다.
  인터넷 연결을 유지하기 위해 유일한 연결인 Wi-Fi를 임의로 끄지는 않았다.
- 다음 비교는 스마트폰을 Bose에 직접 연결해 같은 종류의 소리를 듣는 것이다.
  스마트폰에서 깨끗하면 Jetson 출력·무선 전송 쪽으로, 스마트폰에서도 잡음이 나면
  스피커 또는 공통 무선 환경 쪽으로 조사를 좁힌다. 2.4GHz 간섭은 아직 가설이다.

## 다음 방향 개선의 범위

이하 내용은 기록·말하기 작업 당시의 계획이다. 이후 doyu에서 방향 개선을 구현하고
전체 55개 테스트가 통과했다. 현재 구현·실기기 확인은 [방향 연결 안내](17-direction-timing.md)를 참고한다.

현재는 발화가 끝나 VAD가 오디오를 내보낼 때 USB 방향 읽기를 요청한다. 다음 화자가 이미
말하고 있다면 방향이 해당 자막과 다를 수 있다. 요청 시점만 조금 앞당기는 것으로는
STT 처리 중 쌓인 오디오의 시차를 해결하지 못한다.

다음 작업은 수음 블록의 시각을 VAD까지 전달하고, 기존 방향 워커가 제한된 주기로 저장한
방향 표본을 해당 발화 구간에 연결하는 것이다. 표본 보관 길이·USB 호출 주기를 제한하고,
재연결 세대가 다르거나 표본이 부족하면 방향 미확정으로 표시해야 한다. 검증된 DOAANGLE만
읽으며, 교대 발화·빠른 교대·음성 대기·방향 오류를 테스트해야 한다. 이번 구현에는 포함하지 않았다.
